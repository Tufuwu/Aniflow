# 第一阶段：剧情理解与中文解说

2026-11-15：默认叙事规划后，由程序按节点打包原事件依据，直接整稿写作，不再必经独立事实整理API。所有分析、规划和旧模型清单都作为待核材料；模型整理或确认不等于正确。写作中完成取舍、归并和口语化，后续文字复核、严格原图核验和人工审核继续保留。

有可用上一话摘要的章节，全稿首段第一句简要回顾与本话相关的前情，随后自然转入本话；不新增前情段，也不复述整话。第一话或前情不可用时直接进入本话。程序在写作准备时将摘要引用的上一话事件及原图来源接入首节点，保留历史章节、版本和确定性；锚点及节点数量不变，原规划缓存不改写。写稿、单段修复与定向返修共用这条规则，整稿复核在现有 opening 项检查，回顾句继续参加严格逐句原图核验。来源打包版本升为2，旧候选和不可变版本保留，已审核段落继续锁定。

2026-11-13：增加以故事推进为目标的整话规划与整稿写作，不再按目标时长、事件数或每段字数压缩。新旧证据与人工审核保护继续生效。实现与本轮离线验收范围见 [故事吸引力改造与验收](engagement-acceptance.md)。

剧情审核流程负责本地第一话的分镜分析、剧情证据库、解说稿、事实核验和人工审核，本身不调用 TTS、音频、视频、下载器或后续话。独立的 `preview` 命令负责待审核音视频预览。真正的内容质量需要真人按原作逐段验收，自动测试只能证明数据和流程约束。

## 分阶段交付

1. Story Analyzer + JSON Story Bible：分镜顺序、人物档案、动作、原文对白、关键事件、显式因果、来源哈希。事件及来源 ID 由程序分配；整话读完后复核封面/片尾边界，依据原文和原图补充确切姓名、亲属关系，未知身份继续保留未知。
2. Narrative Director + Script Writer：按重要性选取主事件，用结构化里程碑保证冲突、高潮、规则、目标/代价和剧情结尾不被漏掉。因果前提并入相关主事件上下文，不强制每个特写单独写一段。按阅读顺序组织开场、发展、冲突、高潮和结尾。支持忠实叙事、爽点解说、高悬念。
3. Fact Checker + Review Text：原图和事件对照的逐句核验，四类问题、来源查看、手工修改、驳回、重新核验、单段生成、通过锁定、历史查看、JSON 导出。
4. 离线约束测试、旧传输回归测试、原创人工验收样例、真实第一话试运行。

## 启动

完整 AniFlow 安装完 `requirements.txt` 后，进入原来的 Review Text 页面，新增的中文剧情审核区域和旧旁白功能同时可用。也可以使用没有音视频依赖的入口：

```powershell
python -m pip install flask requests Pillow python-dotenv filelock
python story_app.py import --project first-chapter --source "本地第一话目录"
python story_app.py serve
```

打开 `http://127.0.0.1:8081/story-review?project=first-chapter`。

原始切片先点击“拼接并检测分镜”（需要已安装仓库的 ultralytics / torch / OpenCV）。检测窗口有重叠，最终来源区域按自然留白组织，并避免从完整检测框内部切断。仅压缩纯白间隔，保留全部非白内容和来源坐标；含多个检测框或没有检测框的区域标记 `boundary_uncertain`。区域可能包含多个相邻分镜，分析器需要分别提取其中事件。

来源区域尚未确认时可以预分析和生成草稿，但不能锁定审核。查看输入图片并核对完整性和阅读顺序后，再点击确认分镜。检测不理想时，使用原 AniFlow 的可编辑检测框调整，或将人工整理好的分镜目录导入新项目：

```powershell
python story_app.py import --project first-chapter-reviewed --source "完整分镜目录" --panels
```

`--panels` 表示输入已是完整分镜，不能用它将下载切片冒充完整分镜。检测窗口和自动框可能漏检或截断，分镜完整性需要人工核对。

随后点击“分析剧情”和“规划并生成解说”。核对每段原图、人物、动作和事实问题，必要时编辑后重新核验。模型核验通过才开放“审核通过并锁定”；锁定后不能编辑、驳回、单段重写或整稿覆盖。模型不可用、漏句、结果无效、存在不确定内容都不会视为通过。

也可在已经完成输入准备后运行 `python story_app.py run --project first-chapter --style faithful` 生成草稿。新版先生成整稿并复核叙事连贯性，再逐句核验；明确事实问题和不确定内容会结合反馈最多改写两次，最后重新复核全稿。仍未通过的内容保留问题状态。单段重写同样接收上一轮核验反馈。核验通过只表示模型判断有依据，不等于人工审核完成。

## 模型配置

读取仓库根目录的本地 `.env`，已有环境变量优先。`.env` 在 `.gitignore` 中，密钥不能提交。

```dotenv
STORY_API_BASE=https://api.deepseek.com
STORY_API_KEY=自行在本地配置
STORY_VISION_MODEL=deepseek-flash
STORY_WRITER_MODEL=deepseek-flash
STORY_CHECKER_MODEL=deepseek-flash
```

云端地址不带 `/v1`，复用的兼容传输层会追加 `/v1/chat/completions`。事实核验也读取原图，因此 checker 必须支持图片。不同环节可以指定不同模型名。未设置 `STORY_API_BASE` 时，沿用现有 Ollama / 9router 选择。云端视觉模型会接收到相关分镜图片；使用同一个模型的分析和核验可能产生相同偏差，不能替代人工审核。

DeepSeek 官方端点使用 JSON 输出格式；抽取和写稿关闭额外思考，逐句核验启用低档思考。该选项仅发送给官方 DeepSeek 域名，不影响旧 Ollama/9router 行为。请求记录和缓存键包含这些选项与图片编码参数。

## 数据结构与追踪

每个项目固定存放于 `output/story/<project>/Chapter_00001/`：

```text
inputs.json                    # 只读导入的切片/分镜清单
evidence/<sha256>.<ext>         # 原始证据快照；每次查看验证哈希
preparation/<input_hash>/      # 拼接图、检测窗口、裁切图、框和原始清单
calls/<stage>-<uuid>.json      # 模型、提示词、图片哈希、原始响应或失败原因
cache/<request_hash>.json      # 内容、模型、后端、完整提示词共同决定的缓存
revisions/<uuid>.json          # 不变版本：bible、plan、script、审核结果
current.json                   # 原子更新的当前版本指针
.chapter.lock                  # 跨进程互斥锁
```

Story Bible 包含：`panels`（顺序、图路径、哈希、对白、识别疑点）、`characters`（稳定 ID、姓名、外貌、别名、身份证据）、`events`（事件 ID、动作、人物、重要性、叙事职能、原文/视觉依据、明确因果）。仅有时间顺序不建立因果。

Script 每段都有 `segment_id`、`event_id`、`source_panel_ids`、`context_event_ids`、`section`、`text`、`review_status`、`fact_check`。上下文事件只能来自明确因果前提，其原图也一并进入来源索引和事实审核。事实报告逐句记录文本、判定、问题类型和依据。模型无法改变段落的事件和来源关联。旧旁白不会写入或覆盖新 Story 数据，新 Story 也不会自动覆盖旧的 narration 字段。

每段写作和核验后立即保存版本；中断可查看已保存草稿。分析中的成功模型调用保留缓存，重试分析可复用。整章生成失败后重新生成会使用已缓存的相同调用。显式单段重写和重新核验会绕过响应缓存。所有编辑带当前版本号；旧页面提交被拒绝，防止覆盖别人刚审核的内容。模型调用记录不包含 API 密钥或请求认证头。

已审核段落受保护，整稿重做需要另建项目，旧文案保存在原项目和历史版本中。本阶段没有自动解锁已审核稿的入口。

## API

| 接口 | 用途 |
| --- | --- |
| `GET /api/story/<project>` | 当前状态、历史、输入类型、后台任务 |
| `GET /api/story/<project>?revision=<id>` | 查看历史版本 |
| `POST .../prepare` / `.../confirm_panels` | 拼接分镜 / 确认输入 |
| `POST .../analyze` | 分析剧情 |
| `POST .../generate` | 规划和写稿；可传 style；max_events 仅保留兼容，不限制故事篇幅 |
| `POST .../segments/<id>/<action>` | edit / regenerate / check / approve / reject |
| `GET .../jobs/<id>` | 后台任务进度和错误 |
| `GET .../evidence/<panel_id>?revision=<id>` | 此版本原图证据 |
| `GET .../export` | 含来源、审核状态的最新 JSON；草稿状态不会被隐藏 |

所有写入请求需传 `revision`（初始为 null）。编辑另传 `text`。长任务返回 202 与 job_id。并行同章操作或版本冲突返回/报告冲突。重启后后台任务不会自行续跑，但已提交版本、模型调用和缓存都保留。

## 自动测试及人工验收

```powershell
python -m pytest tests/test_story_pipeline.py -q
python tests/test_llm_transport.py
node --check static/js/story_review.js

```

`tests/fixtures/story_acceptance.json` 是原创三分镜样例，列出正确叙述及人物颠倒、事件反转、无依据亲属关系、错误因果、未来剧情等反例。离线测试使用假模型验证处理这些判定的机制，并不证明真实模型一定识别得出这些错误。

真实章节验收：

- 对照原图检查分镜完整性和阅读顺序，不能把下载切片边界当成分镜边界。
- 全部人物姓名/身份有画面或对白依据；同一人物身份稳定；身份未知时保持未知。
- 无对白动作不能漏；角色说法不直接升级为事实；只保留明确因果。
- 三种风格分别检查：关键事件忠于原作，开场交代必要背景并建立具体关注点，可从世界异常或场景行动进入；高潮不夸大，结尾不编造后续。
- 每个句子的事实能回到对应事件和原图；每段点开证据、通过后锁定，再试重写应被拒绝。
- 对比原图哈希，检查单段重写不改变其他段，检查历史版本可恢复阅读。

自动检测、视觉分析和事实核验都可能出错。第一话的最终“已审核”状态必须由用户在界面中完成，不能用自动模型输出冒充人工验收。

## 生成前资料与跨话延续

同一个项目可按话数分别保存文案：`Chapter_00001`、`Chapter_00002` 等。旧命令和旧接口仍默认第一话。审核页可选择话数，展开“生成前资料”填写本漫画背景和主要人物资料；资料单独保存版本，用于下次分析、规划和写作，不改写旧稿。用户参考资料仍须与漫画证据核对，不直接升级为已确认姓名或关系。

当前保存的世界背景和主要人物设定以后台用途 `input_role=series_settings` 标识，第二步叙事规划直接读取该项目的当前资料版本，单独附送一次background/characters正文；不用重新分析或把资料复制进本话Bible。正文不添加“外部参考”标签、来源编号或链接。旧分析中复制出的同话背景/人物摘要仍从默认输入排除：无用途标记的历史资料及显式analysis_reference不会被程序猜成作品设定，新设定与旧摘要不按关键词或文本外形分类。界面和CLI显式保存的资料默认为作品设定，旧分析导入工具则明确标记analysis_reference。

规划有效缓存绑定设定全文及版本，规划结果仅以settings_basis记录版本和内容哈希；设定变化触发新的规划/候选组，第一步事件整合继续复用。规划提示词为v7、有效缓存合约为4，正常仍只调用direct，不恢复独立规划模型复核。事实整理、写作和复核不再重复附送这份设定正文，继续按当前规划与事件证据执行。第一话的前情仍为空；全作姓名、职业、关系及后续线索不能自动绑定当前C编号、覆盖原分析或提前进入节点标题/兑现。

第二步通过 `planning_material` 自动构造尽可能精简的输入，不追求清除全部语义冗余。动作列表与facets动作逐字且顺序完全一致时省略重复列表，省略本地片段/图片定位编号和约定为空的列表，全部为空的身份揭示表合并成一次状态说明，JSON采用紧凑格式。事件ID、原作顺序、完整facet文字及状态、独有动作、对白、因果、时间与揭示顺序继续保留；人物未知状态及真实/旧版待核身份记录保留，当前背景与主角设定各附送一次。完整来源仍由程序从原Bible解析，不改变核验阶段的数据。

无明确依据的构图、外貌或混合文字继续保留，不按关键词删句，不新增用途分类字段或模型阶段。精简仅作用于direct输入，不改写原始分析、整合结果或其他阶段；缓存合约更新后重新规划，旧缓存与候选保留。当前第一话只读核对从77178字符降至46949字符，减少39.17%，60条剧情记录及248个facet正文均保留；这是输入体积和保留约束的验证，未调用真实模型评估规划质量。

兼容的可选事实整理接口使用 `fact_material`，提示词为Story Digest v3，有效缓存合约为4；默认流程不调用，显式调用时仍沿用已有 `nodes/facts/context_usage` 输出和校验。程序直接写稿也复用其中的结构精简：按规划的事件及上下文范围保留剧情文字、细项角色/状态、对白归属、因果、时间和揭示位置，历史事件继续带historical/history_origin。省略后台版本/定位字段、完全重复的动作、空列表及空身份表，采用紧凑JSON。文字证据仅在普通对白记录逐字相同、来源属于本事件且完整说话者记录与原图分析一致时省略副本；独有描述、不同类型、标点差异、归属冲突和额外不确定性/来源信息保留。

跨话资料索引的版本、哈希和来源不精简，仍供现有context_usage取舍；无资料时保留空索引并改用短说明。事实整理缓存仍绑定完整Bible与完整规划，省略字段变化也会失效；旧缓存和候选不覆盖。抽出的共用结构精简函数不改变第二步实际提示词。当前第一话复用已接受的9节点规划，事实整理输入从98960字符降至55044字符，减少44.38%；60条事件、248条细项、64条对白及40个必保事件保留，181条证据中仅省略60条同源对白副本。此次仅构造输入和离线验证，没有调用事实整理API。

每次完整写稿及定向返修结束后，程序通过模型整理本话大体剧情、新背景、主要人物变化和未完成目标，再用相关原图逐项核对。摘要与稿件、人物、事件和来源范围绑定；缺项、无依据、核对不确定或不可用时保持待核对，不丢正文。摘要核对通过后，还须本稿事实和结构化内容核验有效，才可供下一话自动使用；这不等于人工审核通过。

下一话在分析前读取上一话有效版本，并继承累计背景、人物变化、稳定编号及历史来源。更早事件继续保留，历史图和事件使用带章节的独立编号，不混成本话新事件。已在前话揭晓的姓名在本话之前可用；新身份仍按当前话的揭晓位置控制。写作不必机械复述前情。前话正文或有效摘要内容变化，会使后话旧资料关联失效，要求重新分析核对；仅人审状态变化不机械判为剧情变化。

### 本地入口

下面是入口说明，本轮未执行真实生成：

```powershell
python story_app.py context --project <项目名> --background-file <背景.txt> --characters-file <人物.txt>
python story_app.py import --project <项目名> --chapter 2 --source <第二话图片目录> --panels
python story_app.py run --project <项目名> --chapter 2
python story_app.py revise --project <项目名> --chapter 2
python story_app.py memory --project <项目名> --chapter 2
```

修改已有生成前资料须传 `--revision <资料当前版本号>`。`memory` 仅重新生成和核对摘要，不改正文或人工审核状态，也可在页面点击“重新整理并核对本话摘要”；摘要失败后可用它重试，无需重写整稿。

接口为 `GET/PUT /api/story/<project>/context`、`/api/story/<project>/chapters/<chapter>/...` 和 `POST .../memory`；章节接口继续支持原分析、生成、返修、逐段核验、版本读取和证据访问。CLI 分镜准备使用原有审核入口。当前多话入口覆盖文案与延续资料；剪辑/样片入口仍沿用已有第一话入口。


## 多候选与分析复用（2026-11-13 本地更新）

默认路径现在是：一次漫画分析 → 本话信息整合与事件还原 → 复用叙事规划 → 程序按节点打包事件依据 → 2份候选写稿（可选3份）→ 每份文字复核和引用原句的比较 → 人选定 → 仅选中稿严格逐句看图核验与定向修订 → 整稿复查 → 人工审核 → 原配音/导出门禁。

叙事规划不再额外调用独立的 `story_plan_review` 模型复核。正常只请求一次 `direct`，原有本地校验继续检查ID有效性、非剧情排除、重复引用、节点阅读顺序及模型声明的essential/milestone覆盖；结构或引用错误仍可按原上限重试规划请求。新规划只记录 `planning_validation.mode=program_constraints`，不生成 `completeness_review` 或宣称语义复核通过。未被规划模型声明为必需的语义遗漏留给后续整稿复核，程序覆盖校验无法代替语义判断。规划有效缓存合约升为2以区分旧流程，历史规划、旧复核结果、候选、请求、缓存和人工审核状态保留。按规划整理事实、后续文字复核和严格原图核验继续沿用原流程。

分析版本仍使用 `revisions/`、原图 `evidence/` 和现有 `cache/`。`analysis_revision` 指向不变的纯分析版本；`cache/valid-<hash>.json` 是经过结构、来源和身份约束校验的阶段结果，不是第二套漫画数据库。逐图检查点以实际原图哈希、来源/裁切/准备元数据、分析提示词、视觉模型/后端/图像编码及先前上下文为依赖。一个来源变化仅重做它及依赖其前文的后续来源；此前成功来源继续复用。边界复核和身份复核分别保存检查点，失败不能撤销已成功的分镜分析。原始响应、失败和旧缓存均保留；恢复优先命中已校验结果。身份失败仍可保留未知人物分析，后续单独重试身份阶段。

候选各自保存编号 `K001…`、来源版本、分析依据、表达任务、规划、正文、文字复核和状态。生成接口的 `candidate_count` 表示本风格当前候选组的目标总数2或3，重复提交不重写有效稿，失败候选可用原编号恢复；不同风格保留各组历史。程序按相同规划打包原事件，新稿只记录后台 `source_material_basis={version,hash}`，绑定完整Bible、规划和打包版本，不生成或冒充模型事实清单。它只用于依赖和版本管理，不是可信度等级，也不作为模型输入标签。旧候选和旧清单保留，新默认输入版本单独成组，不能误复用另一版本的成稿。缺少有效文字复核或无适合候选时保持 `needs_review`，不自动重写全组。比较必须引用当前候选原句并说明优点、问题、事实风险与推荐理由；推荐不自动选定。

页面可生成/补充候选、重新文字复核、重新比较、选定，并单独启动“严格核验选中稿并定向返修”。选定只切换当前稿件投影，清除上一选择的摘要关联，不授予事实通过或人工通过。每次编辑、核验和修订同步回对应候选，其他候选不受覆盖。比较绑定当前候选组文本和文字复核；改变正文或依据后显示待重新比较。已人工审核的当前稿继续锁定，不能切换候选或整稿覆盖。

新增接口（同样支持 `/chapters/<chapter>`）：

- `POST .../generate`：`revision`、`style`、`candidate_count`（默认2，允许3）。只走文字阶段。
- `POST .../candidates/review_candidate`：`revision`、`candidate_id`，只重做该稿文字复核。
- `POST .../candidates/compare`：`revision`，只重新比较。
- `POST .../candidates/select`：`revision`、`candidate_id`，仅选定，不调用模型。
- `POST .../candidates/verify_selected`：`revision`，严格核验选中稿，修事实问题、复查整稿并生成/核对跨话摘要。

CLI `run --candidate-count 2|3` 同样停在候选阶段；`candidates --action compare|select|verify_selected --candidate-id K001` 提供分步操作。原内部单稿核验引擎保留为 `generate_verified`，供兼容与旧约束回归；页面和 `run` 默认均使用新流程。本次没有运行这些真实生成入口。

发送给模型的资料与本地完整证据分开：写作使用节点事实、必要规划、精简人物/未知状态/揭晓依据及前情；整稿复核使用正文和相关事件，不发送段落内嵌的逐句报告、语义单元、镜头或时间轴。人物取证历史留在本地，写作不反复发送完整 `identity_evidence`。原图核验仍附当前事件、因果前提、姓名原始证明和必要连续性原图，没有减少严格核验要求。新逐句关联v3绑定正文、事件范围、人物/关系/揭晓依据及相关来源；未涉及的后文事件变化不再使本段核验失效。旧v2关联仍按原有整话指纹验证，不批量改写旧数据。

前情只传大体摘要、累计背景、人物状态事实、主要人物、未完成目标及来源引用；历史事件表/原图和身份取证仍留在Bible中按引用读取。更早背景和未知限制继续保留。摘要问题采用 `patches` 只返回问题条目，程序合并；不能改变已正确条目、人物列表或顺带增加事实。核验复用绑定条目文字、事件、人物/关系及来源原图；只重新核验变化条目。失败保留待审候选和修订上下文，下一次摘要重试可继续补问题条目，不必重写正确摘要。

请求原始用量和结束原因继续留在 `calls/`；`usage/` 追加缓存/检查点命中、请求、失败和重试原因。离线 `python tools/audit_story_usage.py <章节目录>` 汇总各阶段请求次数、已知实际输入/输出/推理token、未知用量、结束原因和复用情况。未知不视为0；输出上限不计入实际消耗，不估费用。模型、思考档位和响应上限沿用原配置。


旧实现保存的 `fact_sheet` 和 `fact_sheet_basis` 继续可读，显式传入时只作待核整理稿。写作、复核和摘要同时保留对应原事件，不能因清单由模型整理就视为正确。新默认流程不生成fact_sheet，直接使用按节点引用的精简事件、原文、人物、历史和未知限制；写稿、返修、比较和摘要均不会暗中补跑事实整理。原图核验与摘要原图复核不受此调整影响。

旧实现曾将超过2000字符的生成前背景和人物资料经 `context_digest` 整理为共享参考简报。2026-11-14 的“本话信息整合与事件还原”已替换默认路径中的参考压缩：分析和生成入口不再调用它，旧函数、缓存及参考原文保留供历史兼容。新步骤直接读取本话完整分析，详见下节。

### 本话事实与补充资料取舍（2026-11-13，离线改动）

在上述机制上继续补充，沿用现有分析、节点事实、候选、版本和审核系统。本话必要世界设定、环境异常、危险限制、行动和转折共同进入事实简表，不另附一份同话背景摘要。事实整理仍返回 `nodes/facts`，新增可选的节点 `context_usage`，逐条记录已有资料来源的用途 `supplement/covered/irrelevant/uncertain` 与理由；该取舍随原事实简表保存，不新增模型阶段。事实整理缓存合约升为3，依赖仍包含完整Bible、规划与模型。同一分析但不同规划的候选也分组保留，不能复用另一规划的成稿。

`context_catalog` 只是已有记忆和版本化参考的来源视图：历史条目保留章节、事件、版本、原图哈希；用户参考保留原版本、条目或原文偏移。`covered` 必须有简表事件覆盖及一致来源，冲突版本、哈希、章节、原图、推测确定性或无来源的重复判断会降为 `uncertain`。相同事件还可能含未整理的必要事实，不能因事件相同便整条删除。无取舍记录的旧稿保持明确待核对，不按标题或关键词猜测。`irrelevant` 的理由及全部原始资料仍在本地，未静默删除。

写作、整稿复核和定向修订使用精简的必要规划、共用事实、人物基本信息、逐节点揭晓限制和按需资料，不默认发送人物描述/取证历史、原始背景JSON或段内逐句报告。跨话前情为 `prior_context`，用户及其他待核参考为 `reference_context`；第一话没有前话时前者为空。未知、用户参考和推测不会被这些文字视图升级为确认事实。候选比较按规划共用一份同样的依据。

写作围绕人物处境、选择、行动、反应和变化展开，必要背景可以在适当位置讲述，候选只变表达与组织，不变事实、时间、因果及揭晓顺序，不增加字数/段数/时长配额。整稿复核保留原结构化检查及逐字原句/节点/事件校验，区分真正影响理解的问题和可选建议；资料存在不等于必须全部写入，无有效问题不重写。去掉反复追加的整份作者规则，合并同义审稿要求。

默认仍只有选中稿进入完整逐句原图核验。原句、事件、身份依据、递归因果与必要连续性原图及其依赖、正确段落复用、人审锁定和正式导出门禁保持原流程。原单稿兼容引擎也保存事实简表以复用；没有有效简表的旧稿继续使用带来源的精简文字证据，不能伪装成已整理结果。

可用 `python -m tools.audit_prompt_inputs <章节目录> --output <章节外的报告路径>` 只读统计写作、整稿复核和原图核验，缺少有效事实简表时不调用模型补造。显式提供 `--historical-digest <历史缓存文件>` 时先核对规划，并将其标为历史快照，不冒充新提示词结果。统计分别列提示词、系统提示、图片来源标签的字符量及附图数，不估算token、费用或质量。详细离线结果见改动记录新增章节。

### 主要人物结构化档案与世界背景（2026-11-14）

按用户后续要求，当前人物档案只维护主要人物，显示姓名、身份、性格、能力，以及需要时的暂时状态。沿用现有 `main_character_ids` 判断维护范围，新名单直接替换旧名单，不自动把所有出现过的人物累加为主要人物；仍属主线但本话未出场的角色可以保留在名单。配角继续留在分析人物识别和原图证据里供严格核验，不建立长期人物档案。页面将两者分别标为“主要人物档案”和“人物识别记录（核验用，包含配角）”。

继续使用原 `chapter_memory.character_states` 存储，不另建人物数据库或新增模型阶段。每条人物更新带 `attribute={field,key,certainty}`，field 为 identity/personality/ability/state/other；姓名只读原严格身份核对结果。key 是同人物属性的稳定键；certainty 分 explicit/observed/inferred/unknown。缺少分类的旧资料保留为未分类，不按描述或关键词自动推断身份、性格、能力。

**当前值直接覆盖**：同人物、同字段、同属性键的新值，在原图逐项核对及源稿严格核验有效后，直接替换当前记录中的旧值；不同能力或不同属性分别保留。没有新依据的字段不清空，推测、未知或未完成核验的更新放在 `pending_facts`，不能覆盖确认值。强制重整同一有效来源时沿用当前已核对字段，避免遗漏字段被清空；来源依赖变化时不复用过期当前记录。原图、原始响应、旧版本及人工审核状态继续由原系统保留，页面当前档案不累计旧值。

一次行为或情绪不能确认性格；能力的直接展示不等于已证实等级、上限或永久属性；角色自述和他人评价须保留说法与确定性。属性分类、确定性及主线作用纳入原摘要逐项原图核对与复用指纹，修改这些字段会重新检查对应条目。保留来源章节/版本、事件、原图哈希及揭晓位置，继承到下一话时继续重映射历史来源与揭晓顺序。

世界背景在页面分为“大概世界观”和“主线事件”：前者复用现有 background，说明必要世界设定、环境异常、规则及限制；后者复用现有 summary，按原作顺序说明目标、冲突、转折、行动和结果。背景同规则键 `rule_key` 的核验通过新值覆盖旧值，主线 summary 使用本话最新整理结果。新展示视图 `character_records`、`world_background` 从已有记录只读生成，不向写作或整稿复核再附送一份重复的人物/世界资料。

本轮只改本地实现、提示词、页面和离线测试，没有更新真实项目记录、调用真实模型/配音API或生成真实正文。旧格式可只读查看；新结构将在下一次由程序和模型流程整理时产生，未离线猜填旧人物属性。


### 本话信息整合与事件还原（2026-11-14，离线改动）

第一步文字处理为 `event_integration`，角色为“本话剧情信息整理员”。程序读取当前 Bible 的完整本话分析，在本地保留原始证据和来源信息，向模型发送输入视图v2：按阅读顺序排列的紧凑片段表，统一使用 `[id,kind,source,status,content]` 列。事件、动作、证据原文、对白、可见文字、场景、设定和未知限制均保留，正文不再与一份冗长的来源目录重复发送。人物索引复用现有 character_index，保留姓名状态、身份疑点、待确认称呼与揭晓位置；重复身份识别历史保留在后台。路径、哈希、裁切映射、坐标及未核验OCR提示不进入模型正文，仍保存在原分析及缓存依赖中。历史事件/原图、跨话记忆和 series_notes 不进入本步骤；跨话因果仅留下 needs_history 标记。已有分析可直接整合，无需重新分析图片。

仅当事件对白与其明确来源图片的对白在文字、说话人、顺序上完全相同时，模型输入才使用该图片的对白片段，不重复附送一份。相同文字在不同来源仍保留独立ID；说话人、文字或来源存在差异时两处原记录均保留，不凭关键词猜测。定点纠错使用同一输入视图，只附问题片段及其明确对白依赖，程序保护正确事件。原始分析、对白与取证历史不被此视图改写。

模型将连续过程归并、在时间/场景/目标/局势变化处拆分；不按口播是否采用、人物是否主角删信息。必要世界规则、危险限制、环境异常、回忆、历史说明分别记录作用和原作时间，揭示位置由引用来源继承；未知、矛盾和未合并片段保留明确状态。描述是连贯剧情梳理，后续叙事规划才选择重点、组织节点与承接；事实简表仍绑定完整当前规划，整稿写作负责自然口播。

输出仍为结构化 JSON。`bible.events` 沿用 event_id/order/summary/character_ids/actions/dialogue/causes/source_panel_ids/importance/role；新增：

- `fragment_ids`、`source_event_ids`：原始片段与原分析事件的精确关联；同一原片段可支持拆分后的多个事件。
- `kind`：current_action/world_rule/recollection/historical_explanation/unresolved/non_story。
- `time.original_time/status`、`reveal_panel_id/reveal_order`：分别记录原作时间与本话揭示位置。
- `facets`：每条包含 role/text/fragment_ids/status，表达前提、目标、阻碍、选择、触发、行动、反应、结果、必要设定或未知限制。缺少的环节不补造。
- `status`、`pending_causes`、`internal_causes`：保留不确定、待补历史、拆分后不明确的因果和合并内部已有的明确因果。

程序按片段 ID 继承原图顺序、对白、证据、人物及已有明确因果，不通过标题、关键词或相似度猜关联。检查所有片段在事件层的覆盖、来源范围、揭示顺序与结构化不确定性；facet引用其文字实际依据的事件内片段，不再要求全部事件引用在facet层重复一次。对白、场景、疑点等原文仍可按事件引用回查；事件层覆盖仍是硬约束，片段ID覆盖不等于语义完整表达。禁止模型另造事件 ID、原图来源和因果。已核对的非剧情边界继续有效，模型不能在整合阶段自行排除剧情或将剧情与非剧情合并。事件数和描述字数不设配额；接口输出容量需显式配置，不能通过省略参数实现无限输出。第一步及其定点纠错在官方 api.deepseek.com 的 deepseek-flash/deepseek-v4-pro 上显式请求 max_tokens=393216（384K，为2026-11-14核对的官方允许最大值），不回落到非思考模式默认8K。这是可用容量，不是要求模型写满，仍受模型上下文和服务端限制。其他接口可用 STORY_INTEGRATION_MAX_OUTPUT_TOKENS 填写其实际支持的正整数容量；未知接口不猜测兼容上限，未配置时保持服务商默认值。其他阶段原配置不变。服务端返回length截断时立即保留失败记录并停止，不按相同参数自动重试；其他传输或JSON错误最多尝试三次。输出容量策略与实际数值进入请求记录和检查点身份。

完整响应先经过本地确定性修正：只有精确存在且属于当前事件的ID才允许将单字符串包成数组、去重及按原片段顺序排列；不删除或替换未知ID，不猜测跨事件来源。facet标为supported而所引来源有未知、矛盾或待补历史时，仅保守下调状态，不改文字或将来源升级。旧分析的uncertainties混有水印、品牌排除说明，本地处理继续保留其原始状态，不按关键词重分类。修正路径、前后值和原因保存在event_integration.local_repairs；原始模型响应和原证据保持原样。这只能维护结构化确定性，不能修正或证明正文语义。

剩余纠错采用 `pipeline/integration_repair.py` 中的字段补丁协议v1，整合输出合约为版本3。程序一次收集独立的字段错误，只发送issues中的问题ID、精确字段位置、当前值、错误、expected结构、允许片段和必要只读上下文。摘要或kind使用本事件来源，facet字段优先只带其已有精确引用；只有不存在的time/facets或无效facet对象才开放对应字段整体，已有有效兄弟字段不授权。材料复用紧凑视图，仅补入精确来源的对白依赖、相关人物约束、关系和待补历史，不发送完整整合事件、全话资料、后台路径/哈希、全局核验索引或另一份背景/人物摘要。

模型只返回 `patches:[{issue_id,value}]` 与 `unresolved:[{issue_id,status,reason}]`。程序按自身白名单将ID映射到字段，不接受模型提供path、完整事件、旧replacements/additions协议、额外程序字段、越界ID、重复/缺失问题ID或不符expected的类型/枚举/来源。补丁中的确定格式错误先复用本地修正再校验，不为已知ID的字符串格式再次调用模型。类型和来源通过的字段保留在本次内存候选中，下一次仅发送仍有问题的字段，最多两次模型纠错；最终仍完整检查片段覆盖、揭示顺序、非剧情边界、来源及结构化确定性。字段前后值记录在event_integration.field_repairs，本地修正另记local_repairs；纠错版本和实际提示词哈希进入整合元数据及有效缓存依赖。

`unresolved` 状态为insufficient_context、insufficient_evidence或requires_scope_change。模型明确返回待处理状态后立即停止，不盲目重试；原始请求/响应及待处理原因保留，不保存部分修复为有效缓存或新版本。来源对应不明、顺序/非剧情边界错误，或整条事件缺失而需要新增事件、改变片段归属时，程序同样明确报requires_scope_change，不猜测归属或绕过字段授权范围。未知事实本身仍可在正常事件中保留未知状态；上述待处理错误不等于自动生成或确认新剧情。

原始事件保存在 `bible.analysis_events`，原始图片、对白、识别记录保持不变；`event_integration.source_revision` 指向不可变来源版本，fragment_index 提供本地路径回查。缓存复用现有 validated_result，绑定实际输入、来源版本、来源哈希、完整提示词、模型/系统角色/后端及输出合约；阶段名称与旧 context_digest 分开，旧摘要不能命中新阶段缓存。后续生成重复执行时复用有效整合；不改写旧候选、旧版本或人工批准状态。人工已锁定及并发版本冲突在调用模型之前拒绝。

输入视图版本及本阶段输出策略也进入缓存身份。模型看不到的图片哈希、来源版本和完整本地分析继续作为检查点依赖；不能因移除后台字段而复用另一来源的结果。旧版本、旧请求及旧有上限的缓存不删除或批量迁移。

可运行 `python -m tools.audit_integration_inputs <章节目录> --baseline-trace <旧完整输入请求记录> --output-dir <章节之外的目录>`，只读导出新模型输入、提示词和字符审计。旧记录必须是同一完整分析和来源版本，否则拒绝比较。审计不创建模型或写入项目缓存，不把字符量换算成token或费用。

已整合章节不会从旧Bible快照重复附送series_notes，也不把无previous_chapter来源的同话summary/background/character_states当作额外前情。当前明确保存的作品设定则按上述独立入口读取，供第二步规划使用，不能与旧同话摘要一起一律过滤。原始参考仍保存，既有原图分析参考功能保留；有固定前话版本的历史记忆只在整合之后按现有规则供规划与事实整理使用，不混成本话新事件。旧章节只读、旧稿返修和旧缓存兼容逻辑不做批量迁移。

页面可单独运行“本话信息整合与事件还原”，查看结构化事件和原作时间/揭示位置。`POST .../integrate`（也支持 `/chapters/<chapter>/integrate`）仅接收当前 revision，只做事件整合；CLI 为 `python story_app.py integrate --project <项目> --chapter 1`。这些运行入口会调用文字模型，本轮只用模拟模型离线测试，未对真实项目执行。默认 generate 和兼容 generate_verified 都先复用/补齐事件整合，再继续各自原流程。

离线测试只能证明 ID、来源继承、覆盖、顺序、状态、缓存依赖和版本/锁定约束。完整覆盖一个片段的 ID 不代表片段内每一项意义都已被正确表达；模型是否合理合并/拆分、必要设定是否讲全、时间和回忆是否正确理解、对白归属、因果与心理是否克制、描述是否连贯，仍需真实模型与人工逐项验证。原逐句原图核验和人工门禁继续有效，不能因事件整合通过结构校验就标为事实或人工审核通过。本轮未调用真实模型、配音 API，也未生成真实讲稿或视频。
